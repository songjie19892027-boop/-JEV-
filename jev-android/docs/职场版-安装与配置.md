# 职场版 · 安装与配置指引

面向：**日常对接领导、需要判断对方言语深意 / 是否推责 / 是否甩锅 / 是否派活** 的使用场景。

---

## 一、这一版跟原来有什么不同

| | 原来（生活版） | 现在（职场版） |
|---|---|---|
| 判断对象 | 男女对话 | 上级领导发来的工作消息 |
| 判断题 | 感情类（是不是喜欢你…） | 是否有深意 / 推责 / 派活 / 只是知会 / 要不要留痕 / 隐含时限 |
| 判断模型 | 本地 Qwen3-0.6B（已停用） | **DeepSeek 云端大模型** |
| 输出 | 只给判断 | 判断 + 话术建议 + **留痕提示** |
| 额外新增 | — | **关键词规则层**（本地词表，不经模型） |

> **为什么要换掉本地模型**：原来的 0.6B 小模型是在**对局数据**上训的，不是中文对话。
> 实测把 5 段逻辑完全相反的话喂进去，同一道是非题的概率全落在 84% 上下，
> **极差只有 1.8 个百分点** —— 等于根本没读输入。这不是调参能修的，是模型能力问题。
> 详见 `tools/probe_state_sensitivity.py`（旧工程）与 `tools/verify_deepseek.py`（新）。

## 二、实测结论（2026-09-23 真实跑过）

判断通道已跑通，而且**模型确实在读对话**。核心指标是「分离度」—— 把逻辑相反的场景喂进去，
同一道是非题的概率必须被拉开。

| 是非题 | 最低 | 最高 | 极差 |
|---|---|---|---|
| 有没有话外之意 | 0% | 90% | **90pt** |
| 是否把责任推给你 | 0% | 95% | **95pt** |
| 是否派了本不属于你的活 | 0% | 75% | **75pt** |
| 只是知会还是要你动 | 0% | 95% | **95pt** |
| 要不要留文字记录 | 0% | 90% | **90pt** |
| 有没有隐含时限 | 0% | 90% | **90pt** |

判据是 ≥25pt，**六题全部达标，最低也有 75pt**（作为对照，旧的本地 0.6B 模型只有 1.8pt）。

几个能说明「它真的看懂了」的旁证：

- **空对话（只给背景、没有任何消息）→ 六题全是 0%** —— 没内容就不编
- 「食堂中午有盒饭」这类无关消息 → 推责 0%、派活 0%
- 「这次客户反馈很好，你做得不错」正面表扬 → 推责 0%
- 越界派活那句话 → 派活 75%，同组里推责只有 10%（**没有混为一谈**）

> ⚠️ **数字会浮动**：模型带 0.2 温度，同一句话跑两次，单题概率差约 ±10pt。
> 方向（哪题明显偏高）稳定，别抠具体数字 —— 真正该看的是「哪一题超过 60%」。

面板实测长什么样：`docs/panel_preview.html`（三例全为真实数据）。
完整报告：`docs/deepseek_verification.html`。

## 三、密钥申请（5 分钟，唯一需要花钱的地方）

1. 打开 **https://platform.deepseek.com**，用手机号或邮箱注册。
2. 左侧菜单 → **API Keys** → 点 **创建 API Key**。
3. 复制出来的那串 `sk-` 开头的字符串。
   > ⚠️ **只显示一次**，关掉就看不到了，先粘到备忘录里。
4. 左侧菜单 → **充值**，充 **10 元**先试。
   > 判断一次对话大约消耗 800 输入 + 200 输出 tokens。按 DeepSeek 现价，
   > **10 元大约能判断 3000～5000 次**，日常用一两个月没问题。

## 四、装 App 并填密钥

1. 装 APK（在工程根目录）：

   ```bash
   adb install -r jev-assistant-local-nanojev-release.apk
   ```
   > 实际文件名见工程根目录，就是那个 `jev-assistant-local-nanojev-release.apk`

2. 打开「Jev 聊天助手」→ 进 **设置**。
3. 按顺序填：

   | 设置项 | 填什么 |
   |---|---|
   | **DeepSeek 密钥**（标着「必须填」） | 刚才复制的 `sk-...` —— **只填这一个就够了** |
   | 判断模型 | 留默认 `deepseek-chat` 即可 |
   | OpenRouter 密钥（备用通道） | **留空**。判断和候选回复都走 DeepSeek 了 |
   | 本地 NanoJev | **已停用**，不要填 |

4. 回到设置页上方，点 **连通测试**。
   - 会拿一句演示消息去试：`上次说的那个报表你跟一下，我这两天要用`
   - 成功 → 直接能看到风险等级、关键词命中「疑似派活 · 你跟一下」和「暗中施压 · 这两天」。
   - 失败 → 见下面第六节的错误码对照。

5. 按主页向导开三项权限（缺一不可）：
   - **无障碍**（读消息）
   - **悬浮窗 / 显示在其他应用上层**（展示分析面板）
   - **自启动 + 省电无限制**（小米 / HyperOS 必做，否则后台被冻结、读不到消息）

> 密钥只存在 App 私有存储，不出设备、不进日志。

## 五、面板怎么看

面板从上到下固定这个顺序（**最要紧的排最上面**）：

| 顺序 | 区块 | 怎么用 |
|---|---|---|
| 1 | **风险 N / 10** + 一句话定性 | 一眼扫，红了再细看。定性按**主因**换措辞：推责说「有推责迹象」，派活说「有派活迹象」，只有弦外之音说「有弦外之音」；判断不出主因则说「需要留意」 |
| 2 | **一句话结论** | 只在单题把握 ≥60% 时才出现；不出现不代表没问题，代表模型也在犹豫 |
| 3 | **话术特征（本地规则命中）** | **最可信的一层**，会把命中的原词摊开给你看 |
| 4 | **五道是非题** | 有深意 / 推责 / 派活 / 只是知会 / 隐含时限。两行都列、按概率降序，**不用自己反着想** |
| 5 | **建议留痕** | 只在把握 ≥60% 时出现。出现就用文字复述一遍请对方确认 |
| 6 | **辅助参考**（对方想要什么 / 最佳应对） | 多选题模型判断力有限，**别当结论**，当提示 |
| 7 | **候选回复** | 点「复制」或「填入」，**发送永远你自己点** |

**看板原则**：先信第 3 层（规则），再信第 4 层里概率高的是非题，最后才参考第 6 层。第 2 层的结论本质上是第 4 层的一个摘要。

**第 1 层为什么按主因换措辞**：推责和派活是两回事，应对方式也不同 ——
推责要争**事实**（拿出记录、对齐时间线），派活要争**边界**（问归口、要资源）。
都写成「有推责迹象」会误导你往错的方向准备。主因只取三题里概率最高的那项，
且**必须 ≥60% 才点名**，不确定就退回中性措辞。

## 六、出错对照表

| 现象 | 原因 | 怎么办 |
|---|---|---|
| `DeepSeek 密钥无效（401）` | 密钥复制错了 / 已删除 | 去 platform.deepseek.com 重新复制 |
| `DeepSeek 账户余额不足（402）` | 余额用完了 | 充值 |
| `DeepSeek 请求过于频繁（429）` | 短时间发太多 | 等几秒 |
| `连接 DeepSeek 超时` | 手机网络问题 | 切 WiFi / 流量重试 |
| `无法解析 api.deepseek.com` | DNS / 网络不通 | 检查手机网络 |
| 面板一直不出现 | 权限没开全 | 悬浮窗权限 + 自启动 + 省电无限制，三项都要 |
| 气泡过一会儿消失 | 国产 ROM 杀后台 | 在微信里再交互一下会自愈；根治见「已知限制」 |

## 七、验证判断准不准（可选，但建议做一次）

工程里带了两个脚本：

```bash
cd <你克隆下来的仓库>/jev-android

# 1) 文案稽核：确认 APK 里是新版文案、旧文案已清干净
python3 tools/audit_strings.py

# 2) 端到端实测：把 9 个场景发到 DeepSeek，看模型是不是真的在读对话
#    密钥二选一：设环境变量，或把密钥写进 nanojev/.deepseek_key（一行纯密钥）
export DEEPSEEK_API_KEY=sk-你的密钥
python3 tools/verify_deepseek.py --html --draft

# 只重跑候选回复起草（省 9 次判断请求，改起草 prompt 时用）
python3 tools/verify_deepseek.py --draft-only
```

第 2 个脚本输出五张表，**核心是表 2 的「分离度」**：

- 它把 5 段逻辑相反的话（明显推责 / 正面表扬 / 我自己认责 / 完全无关 / 空对话）都发一遍。
- 同一道是非题的概率**必须被拉开 ≥25 个百分点**，才算「真的在读对话」。
- 如果又出现「所有场景都是 84% ± 1」——那就是模型侧出了问题，先别信任何判断结论。
- 表 4 额外验候选回复的**格式与差异度**（3 条是不是真的策略不同，而不是三句同义改写）。

跑完会生成 `docs/deepseek_verification.html`，可以直接打开看。

> 脚本里的判断 prompt 与 `JevClient.kt` 的 `buildJudgePrompt()` 是**逐字对应的两份**，
> 起草 prompt 与 `draftViaDeepSeek()` 同理。**改判据必须两边同时改**，否则你验证的
> 就不是手机上跑的那套 —— 这个坑已经踩过一次（中文版漏了英文版的一个限定词，
> 导致「隐含时限」在正常派活场景上误报 90%）。

## 八、想自己改规则

关键词词表在 `app/src/main/java/com/jev/probe/jev/JevWorkRules.kt`，
就是四个类别下的一串短语，**直接加词、删词即可，不需要重训模型**：

| 类别 | 收什么 | 例 |
|---|---|---|
| `ASSIGN` 疑似派活 | 把活推给你的句式 | 你看着办 / 你跟一下 / 顺手把 / 你比较熟 |
| `BLAME` 疑似推责 | 把因果反过来讲 | 出了问题你负责 / 我之前不是说过了 |
| `PRESSURE` 暗中施压 | 不给期限地催 | 我只要结果 / 你自己把握 / 这两天 |
| `NOTIFY` 像是纯知会 | 明确不用你动 | 同步你一下 / 不用回复 / 供参考 |

**收录原则：宁缺毋滥。** 像「辛苦你」「尽快」这类中性场合也常用的说法**故意没收** ——
收了会让几乎每条消息都报「疑似派活」，反而没法看。

规则之间如果存在包含关系（`你负责` ⊂ `出了问题你负责`），
只保留长的那条，避免同一句话被同时报成「派活」和「推责」。

改完重新编译：

```bash
./build_apk.sh assembleRelease
```
